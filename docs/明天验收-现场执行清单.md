流程：识别 → 看结果框里的抓取高度说明 → 用尺子量一下罐子实际位置对比 → 再执行。

结果框会打印这几行，**执行前先看它**：

```
抓取高度规则：顶点与中心的中点｜物体高 146.5mm 顶面 146.5mm｜伸进夹爪 36.6mm（腔体 80mm）
夹持宽度 57.0mm

判断标准：

| 看什么 | 正常 | 不正常说明 |
|---|---|---|
| 物体高 | 与实物相符（雪碧罐 146.5mm） | CAD 缩放或位姿错了 |
| 顶面 | ≈ 物体高（罐子坐在桌面上） | 位姿的 Z 错了 |
| 伸进夹爪 | ≈ 物体高/4，且 < 65mm | 超了会被自动抬高并提示 |
| 夹持宽度 | 与实物直径相符 | 认错物体了 |
| 顶面交叉校验 | 差 < 20mm | 差得多 = 缩放错，会被直接拒绝 |

确认无误后加 `--enable-robot-motion` 重启，UI 里还会再确认一次。

## 3.5 UI 操作（两条路径）

**单目标**（每一档的常规做法）：

```
拍照识别 → 点画面里的物体（单击选中）→ 计算选中目标 → 看坐标 → 执行抓取

**多目标**（连着抓几个）：

```

```

- 单击 = 选中，双击 = 选中并加入序列；点错用【− 撤销末项】
- 拍照后默认选中**置信度最高**的那个（原来是检测顺序第 0 个，跟置信度无关）
- 目标框重叠时（第二、三档的遮挡场景）点到**面积更小**的那个 ——
  点瓶子露出的上半部分就选瓶子，点前面的水果就选水果

## 3.6 多物体放置：槽位与已放置区域

连着抓多个时，流程是 抓 → 放 → 回复位 → **重新拍照** → 继续抓。这会连锁出三个问题，
都已处理：

| 问题 | 处理 |
|---|---|
| **堆叠**：都放同一点，第二个落在第一个上面必倒（违反"放置时需要直立"） | **槽位**：每放成功一个前进一格 |
| **二次识别**：重新拍照时刚放好的物体还在桌上，会被再抓一次 | **排除区**：落在已占用槽位 45mm 内的检测结果不参与抓取 |
| **遮挡**：放好的物体挡住还没抓的目标 | 放置区设在 X 负半轴**外侧**，远离桌面中央杂物区 |

当前 4 个槽位（用户系 mm，沿 −Y 排开）：

```
(-170, 170)  (-170, 70)  (-170, -30)  (-170, -130)
```

- 只有**真的放成功**才占用槽位；dry-run 和失败都不推进
- 用满 4 个会明确报"放置区已经用满"，**不会回绕**（回绕就是堆叠）
- 手动把放好的物体拿走后，点【重置放置区】

> ⚠️ 第 2 步的空载可达性验证要**同时验第 0 号和最后一号槽位**
> ——`(-170, 170)` 和 `(-170, -130)` 各走一次。

## 出问题时的三个最可能原因

### A. 机械臂完全不动，但夹爪照常开合

复位点安全闸门在**远程模式**下拒绝每一条运动指令，并且**每拒绝一次就把伺服下电
一次**；而夹爪走 `0x3601` DOUT，是另一条码路，所以照常工作。

→ **切回示教模式**（实测示教模式下 40+ 条 MOVL 全部成功，远程模式 15 次全拒）。

详见 `docs/纳博特C1102-现场真相-必读.md`。

### B. 提示"伺服未能进入运行态"

安全闸门刚把伺服打掉了。现在每条运动前都会自动重新使能并校验，报错说明重新使能
也失败了 —— 检查示教器是否有未清报警、是否还在远程模式。

### C. 抓取被拒绝，提示"机械限制不是软件问题"

物体比夹爪可用张开还宽。当前配置 `jaw_max_open_mm: 85`（**目测值，未实测**）。
如果你们量出来更大，改 `competition.yaml` 的 `gripper_geometry.jaw_max_open_mm`。
苹果实测 75mm 是全场最宽的物体。

## 附：CAD 格式与纹理（2026-08-22 排查结论）

**GLB 不能直接喂给 FoundationPose。** 它的 `Utils.make_mesh_tensors` 是：

```python
if isinstance(mesh.visual, TextureVisuals):
    img = np.array(mesh.visual.material.image.convert('RGB'))
```

GLB 加载后是 `PBRMaterial`，`.image` 恒为 `None`（纹理挂在 `baseColorTexture`），
直接 `AttributeError` 崩。已在 `adapters/foundationpose.py::_normalize_visual`
统一归一化：

| 模型 | 纹理情况 | 归一化后 |
|---|---|---|
| `cola.glb` | baseColorTexture 467×1830 | → SimpleMaterial，走**纹理**分支 |
| `nescafe.glb` | 无纹理，仅纯色 [37,14,5] | → ColorVisuals，走**顶点色**分支 |
| 全部 OBJ | 原样 | **完全不受影响** |

> ⚠️ `nescafe` / `orange` / `lemon` **没有纹理**，只有单一颜色。
> render-and-compare 的信息量明显更少，位姿精度会比有纹理的 `cola` / `sprite` 差。
> 要跑这几个物体，先单独验一次识别精度再上抓取。
