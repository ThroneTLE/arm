# 运动控制"参数错误"排障方向（RTL-22.07 / MOKA MR07S-930 / Inexbot C1102）

> 性质：只读分析（2026-08-22）。依据：学校《系统操作手册》V2207 PDF + 本地
> `manuals/纳博特官方文档/json协议-22.07/*` 官方 22.07 JSON 协议原文。
> 目标：说明"为什么能回读、不能运动"，给出按概率排序的根因清单、判据、安全首测序列。
> **不修改任何代码**；供正在解决运动问题的会话参考。

---

## 1. 现状拓扑（已闭环的部分）

| 链路 | 端口 | 命令 | 状态 |
|---|---|---|---|
| 姿态/坐标回读 | 7000 | 0x9512 → 0x9513（realPosPCS/MCS/UCS/ACS） | ✅ 与示教器一致 |
| 位置查询 | 6001 | 0x2A02 → 0x2A03 | ✅ |
| 操作模式查询 | 6001 | 0x2102 → 0x2103（mode=1 远程） | ✅ |
| 当前工具手 | 6001 | 0x380B → 0x380C（工具手1） | ✅ |
| DOUT 气阀 | 6001 | 0x3601 写 / 0x3602 回读 | ✅ |
| **运动（MOVL/MOVJ）** | 6001 | 0x4502 / 0x4501 | ❌ **报参数错误** |

回读走的是**只读服务（7000）+ 查询类命令**，与运动是两条完全不同的路径：
运动路径额外依赖**伺服使能状态、当前工具手/用户坐标状态、模式**，且 0x45xx 的参数
数组（长度/单位/枚举）此前从未实测过——"能读不能动"完全不矛盾。

## 2. 官方文档对 0x45xx 的确定性结论（先对齐基线，再怀疑代码）

1. **帧格式**：0x4E66 + Length(仅JSON) + Command + JSON + CRC32(Length+Command+data)。
   查询已验证，无问题。
2. **命令字**：0x4501 MOVJ（vel=速度百分比 1~100）、0x4502 MOVL（vel=mm/s 1~1000）、
   0x4503 MOVC、0x4504 MOVS。均**无应答帧**（与 0x3601 相同，fire-and-forget），
   失败以错误提示帧异步推送（见 §4）。
3. **请求体只有 4 个字段**：`robot`(1..4)、`vel`(int)、`coord`(int)、`pos`(数组)。
   **没有** shape/形态、工具号、用户号、加速度字段 —— 工具/用户由控制器"当前选择"决定。
4. **pos 数组 = 7 位**：`[6个本体值, 第7位保留]`。权威依据：0x2A03 参数说明
   （04-6000-机器人设置.md 第 330 行）：“坐标值用7位存储。前六位为 J1~J6 轴角度值
   (**度**) 或直角/工具/用户坐标 XYZ(**毫米**)，四到六位为 ABC 坐标值(**弧度**)，
   **第七位保留**”。现场 0x2A03 实测返回也是 7 位、第 7 位 0.0 → 当前代码
   `[x,y,z,a,b,c,0.0]` 与系统自身格式一致。
5. **coord 枚举**：0 关节 / 1 直角 / 2 工具 / **3 用户**。多处一致：
   - 0x2A02/0x2A03 参数说明：`0-关节,1-直角,2-工具,3-用户,4-电机位置`；
   - 0x2201/0x2203 坐标模式（06-6000-伺服状态.md）：`0关节/1直角/2工具/3用户`；
   - 0x2A12 坐标转换 pos[1]：`0-关节,1-直角,2-工具,3-用户`；
   - 位置变量 data[1,2]（系统操作手册）：`2,1-工具；3,1-用户`。
   **唯一反例**：03-6000-机器人运动.md 写 `2-用户,3-工具` —— 判定为官方文档笔误。
   ✅ 当前代码 `motion_coord=3`（用户1）正确；且 UCS 回读与示教器一致，
   进一步反向证明"3=用户"语义在本机成立。
6. **单位**：关节=度；直角/工具/用户 XYZ=mm、ABC=弧度。当前代码一致。

> 结论：**帧、命令字、pos 长度、coord 值、单位——代码与官方文档全部一致。**
> 所以"参数错误"更可能来自**前置状态**（未使能/当前坐标系状态）而非字段本身；
> 但仍需按 §5 做隔离实验，排除"文档与实际固件实现不一致"的可能性。

## 3. 根因假设排序（按概率）

### ① 未先"伺服上使能"——最可能的缺失前置步骤
官方 22.07 文档 06-6000-伺服状态.md §5.7：
> **0x2311 MAN_BEG_OPERATION `{"robot":1}` —— 伺服上使能（示教盒无该指令）**

即：**上位机运动前必须发 0x2311**，示教器上没有对应按钮（示教器路径是 0x2301
DEADMAN 上/下电）。现场记录里 0x2311 从未验证过；若伺服未上电，运动指令被拒
（表现为错误提示，措辞可能正是"参数错误/无法运动"一类）。

相关查询/设置命令（文档确认，均未实测）：
- `0x2001` 伺服状态设置 `{"robot":1,"status":0}`（**0=真实伺服，不是开关！**）；
- `0x2002`/`0x2003` 伺服状态查询：status **0 停止 / 1 就绪 / 2 错误 / 3 运行**；
- `0x2301` DEADMAN_STATUS_SET `{"deadman":0/1}`（上下电，示教器路径）；
- `0x2302`/`0x2303` 上下电状态查询；
- `0x2101` 操作模式设置 `{"mode":0/1/2}`（主机可设！现场靠钥匙=1 远程）。

### ② 当前工具手 / 用户坐标号状态不对
0x45xx 没有工具/用户字段 ⇒ 用控制器"当前"选择。系统操作手册原文警告：
> "点位绑定工具手2，使用工具手1 运行 → 控制器报错（机器人1 工具坐标使用错误，
> 点位用户为1，实际使用用户2）"；用户坐标同理"若运动时用户坐标和点位参数绑定
> 的用户坐标系不同，则无法运行"。

虽然 0x380B 查得工具手=1（✅），但**当前用户坐标号从未查询过**：
- `0x3C0B`/`0x3C0C` 用户坐标号查询/返回；`0x3C0A` 用户坐标号设置（均在命令字附录，
  详细 payload 未翻译，需对 open.inexbot 原文）；
- 若"当前用户"为 无/0，coord=3 的用户坐标运动会被拒。

### ③ pos 数组变体（隔离实验，低优先级但值得做）
- A：`[x,y,z,a,b,c,0.0]`（现用，=0x2A03 自身格式，最可能正确）；
- B：`[x,y,z,a,b,c]`（6 位）；
- C：照抄 0x2A03 返回的 pos 原样 7 位下发（同值核对，见 §6）。
关节坐标系 MOVJ 同理（角度制：`[J1..J6, 0.0]`）。

### ④ 环境类：EtherCAT / 伺服链
现场记录遗留项：MSR1616NT **RUN 灯橙色闪烁 = EtherCAT 组态未完成**，若持续橙闪且在
运行模式报"Ethercat 主站启动失败/伺服未连接"——运动必然失败。
- `0x5042`/`0x5043` 伺服连接状态查询（servoType）先测。

### ⑤ 文档与固件不一致的兜底项（确认它不是死路之前不要深挖）
- 若 0x2202/0x2203 查得当前坐标模式与预期不符 → 用 `0x2201` 设置；
- 若报错提及"第7轴/外部轴" → `external_axes` 配置问题（当前 0）；
- 若错误 = `0x2B03 code=25530 "转发[0x7266]失败或者无效"` 同类反馈 ⇒ **command 被
  判"无效"，即该固件不支持 0x45xx**（详见 §4 判据，这是唯一需要立刻换通道的死路）。

## 4. 如何拿到"确凿证据"（最高价值一步）

错误永远不会"无声"：0x2B03（错误提示）/ 0x2B04（警告）/ 0x2B05（消息条）/
0x6010/0x6020/0x6030/0x6040（服务器/机器人/控制器/内存错误）。**先抓原始帧**：

| 现象 | 含义 | 下一步 |
|---|---|---|
| 回 0x2B03 + code + message | 命令执行被拒（参数/状态校验类） | 记 code，对照纳博特 2207 错误码表（本地无表，需向纳博特/摩卡索取；或看示教器报警页同码） |
| 回 0x6020/0x6030 | 机器人/控制器状态类错误 | 多半是使能/EtherCAT/超程类，转 §3-①②④ |
| 回 0x2B03 code≈25530 且 message 含"转发[0x7266]失败或者无效"字样 | **该命令字不被支持/无效** | 停 0x45xx 路线，换通道：0x3003 完整点位 / Modbus 502 / 远程程序触发（防死路！） |
| 无任何回帧、超时 | 命令没走到处理层 | 检查消息是否被丢弃（心跳信号确认链路） |

> 提示：UI 报错文本之前，先打印**原始帧 hex**（命令字 + JSON），比报错文案信息量大得多。
> 0x2B03 的 code 是 22xxx/25xxx 之类的编号，纳博特内部错误码表（官方《调试手册》
> 或《报警手册》）可查，问摩卡要 2207 版。

## 5. 安全首测序列（给正在做的会话参考，动之前必读）

**前置**：示教器在线、钥匙已切远程（mode=1）、人站急停旁、夹爪气阀已由上位机接管
（DOUT15/16，运动前确保夹爪关闭状态且无工件）。

1. 只读体检（全部 6001，一条条查询并记录回帧）：
   `0x5042` 伺服连接 → `0x2002/0x2003`（status：0停止/1就绪/2错误/3运行）
   → `0x2302/0x2303`（deadman）→ `0x2202/0x2203`（当前坐标模式）
   → `0x380B`（工具手）→ `0x3C0B`（**用户坐标号**）。
2. 上使能：`0x2311 {"robot":1}`（必要时 0x2301 deadman=1），再 `0x2003` 确认
   status=1 就绪（或 3 运行）。
3. **同值核对**：`0x2A02` 读当前 pos（7 位），原样 MOVJ `{"robot":1,"vel":5,"coord":0,
   "pos":[同值]}`——只验证"这条命令能不能被接受"，机器人理论上不动。
4. 小步验证：MOVJ 关节 ±0.5°（vel 5%），确认移动方向与示教器一致。
5. MOVL 用户1 系：先 coord=3、7 位数组、vel=50mm/s、步长 ≤10mm（UI 步进已有），
   同值→小步→回读核对（0x2A02 coord=3 或 7000 realPosUCS）。
6. 若第 3 步就报错 ⇒ 回到 §4 抓帧判据分层；若报"无效/25530"⇒ 换通道防死路。

## 6. 代码侧现状核对（只读结论，未改动）

- `ros_ws/.../adapters/nexbot_tcp.py`：
  - `_send_motion` 发送 `{robot, vel, coord, pos}`，pos=7 位、Cart ABC=弧度、coord=3，
    **与文档一致**；
  - `move_to`：`axes=[xyz_m*1000, abc_rad, 0.0]`（7 位，第 7 位 0.0，符合"第七位保留"）；
  - **未在任何运动路径发 0x2311 上使能**（候选根因①）；
  - `stop()` 发 0x2314 当"急停"——**官方 06 文档注明"原2314为伺服下电，程序中
    不存在"，现 0x2314=MAN_END_OPERATION（手动操作结束）**；语义存疑，调急停时勿
    被它误导（物理急停/教会模式按键仍是第一保险）。
  - `_wait_motion_finish` 轮询 7000 axisVel —— 前提是运动真已启动。
- `competition.yaml`：`motion_coord: 3`、`pose_frame: UCS`、`port_motion: 6001` ✅。
- 单元测试均基于**本地假控制器**，假服务器从不校验"使能/坐标系状态"——
  所以离线全绿、真机报错的空隙，恰在 §3-①②。

## 7. 一句话结论

> 回读走 7000 只读服务，运动走 6001 0x45xx，二者前置条件不同；
> 当前代码的帧/参数/单位/坐标枚举与官方 22.07 文档逐项一致，**"参数错误"最可能是
> 缺失"伺服上使能(0x2311)"或"当前工具/用户坐标状态不符"**；抓一次原始错误帧
> （命令字+code+message）即可一锤定音；若错误帧为"转发失败/无效"类（25530 同家），
> 立即换 0x3003/Modbus/远程程序通道，避免在 0x45xx 上走到死路。
