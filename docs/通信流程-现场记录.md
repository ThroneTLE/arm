## 1. 网络接入（关键！避免踩坑）

### 1.1 控制器没有独立"上位机网口"

C1102 只有 **2 个 RJ45**：
- **EtherCAT 口** → 伺服链（主控 → 伺服×N）→ 链尾回到 **MSR1616NT**（EtherCAT IO 板）；
- **Ethernet 口** → 示教器转接盒（示教器）。

上位机（电脑）没有直插口。**官方支持方案（已验证可行）**——用 5 口小交换机共享"示教器"口：

```
电脑 (192.168.1.100) ──┐
                       ├── 5口交换机 —— 控制器 Ethernet(示教器) 口
示教器转接盒 ──────────┘
```

出处：22.07《IO_Modbus与远程功能使用手册》6.5.5"Modbus触摸屏使用流程"第(5)步——
"将触摸屏 RJ45 网口、示教器网口、控制器『示教盒』网口连接到同一交换机上"。

### 1.2 排障速查（都是实测过的坑）

| 现象 | 原因 |
|---|---|
| 链路 100M up，但 ping/ARP/DHCP 全部无响应 | **插了 EtherCAT 口**（EtherCAT 100M 协商成功但永不回复 IP 帧；MSR1616NT 的进出两口都是 EtherCAT，MSR1616NT 的空闲口是 EtherCAT **OUT 级联口**，也不是上位机口） |
| 插了"示教器"口但电脑没 IP | 该口是静态 IP 链路，无 DHCP；电脑需同网段静态 IP |
| 网段扫不到控制器 | 控制器默认 **192.168.1.200**（实测；官方文档示例 192.168.1.13/1.20 各不同，以现场为准） |

### 1.3 IP 分配（实测）

| 设备 | IP | 备注 |
|---|---|---|
| 控制器 | **192.168.1.200** | 开放端口：22, 53, 502, 5000, **6001**, 7000（1~10000 全扫结果） |
| 示教器 | 192.168.1.245 | 开放 22 |
| 电脑 | 192.168.1.100/24 | 手动配置（Ubuntu: nmcli 静态 + `ipv4.method manual`） |

## 2. 通信协议（22.07 系，帧格式已验证）

### 2.1 帧格式

```
4E 66 | Length u16 BE | Command u16 BE | JSON数据(UTF-8) | CRC32 u32 BE
```

- `Length` 只含 JSON 数据长度（不含 SyncByte/命令字/CRC）
- `CRC32` 计算范围 = Length + Command + data，**大端**发送，`zlib.crc32(body) & 0xFFFFFFFF`
- 控制器 = 服务端，上位机 = 客户端；TCP

Python 参考：

```python
def frame(cmd: int, payload: bytes = b"") -> bytes:
    body = struct.pack(">H", len(payload)) + struct.pack(">H", cmd) + payload
    return b"\x4e\x66" + body + struct.pack(">I", zlib.crc32(body) & 0xFFFFFFFF)
```

### 2.2 端口分工（实测校准版）

| 端口 | 用途 | 状态 |
|---|---|---|
| **6001** | **实时命令口**（运动/伺服/模式/IO/变量/运行控制） | ✅ 实测可用（文档写 6000，**本机在 6001**！6000 不存在） |
| **7000** | 上位机状态查询（只读：坐标/速度/IO/变量/轨迹） | ✅ 实测 `0x9512`/`0x9513` |
| 502 | Modbus TCP 从站 | ✅ 实测可读（寄存器映射稀疏，需《Modbus地址码列表》xls） |
| 5000 | 文件传输（作业/配置备份） | ✅ 开放 |
| 22 | SSH（OpenSSH 6.6.1 Ubuntu-2ubuntu2.7） | 开放，未登录使用 |

> ⚠️ 心跳 `0x7266`：发送后控制器回 `0x2B03` `{"code":25530,...}`（内容为"转发[0x7266]失败或者无效"）——**可以忽略，直接发正式命令即可**。

## 3. 从头连接流程（实测顺序）

1. 网卡配置（Ubuntu 示例）：

   ```bash
   nmcli con mod "有线连接 1" ipv4.method manual ipv4.addresses 192.168.1.100/24
   nmcli con up "有线连接 1"
   ping -c1 192.168.1.200     # 通 = 物理+IP 层 OK
   ```

2. **7000 端口验证（最稳的第一步，只读）**：
   发送 `0x9512`：

   ```json
   {"channel":1,"robot":1,"mode":0,"queryType":["realPosACS"]}
   ```

   原始帧：`4e66003b95127b226368616e6e656c223a312c22726f626f74223a312c226d6f6465223a302c22717565727954797065223a5b227265616c506f73414353225d7d<CRC>`
   回复 `0x9513`：`{"channel":1,"replyData":{"realPosACS":[J1..J6,度]},...}`，CRC 用 `zlib.crc32`
   复核置 OK。→ **这条通了，控制器身份/固件/链路全部确认。**

3. **6001 端口连接**（实时命令口）：

   a. 位置查询：`0x2A02` `{"robot":1}` → 回复 `0x2A03`
      `{"configuration":8,"coord":0,"deg":0,"pos":[J1..J6],...}`（config=8 为关节坐标，deg 说明角度）
   b. 操作模式：`0x2102` `{}` → `0x2103` `{"mode":1}`（0 示教 / 1 远程 / 2 运行）
   c. DO 状态：`0x3602` `{}` → `0x3603` `{"status":[16×0/1]}`（16 路 DOUT 从 1 开始）
   d. **DO 控制（夹爪气阀！）**：`0x3601` `{"port":15,"status":0}` / `{"port":16,"status":1}`
      —— 无应答帧，用 `0x3602` 回读确认。

4. （下一步预留）运动：`0x4501` MOVJ `{"robot":1,"vel":5,"coord":0,"pos":[7 个值]}`
   —— **尚未实测**，见第 6 节安全性检查清单。

## 4. 夹爪气阀控制（已验证）

### 4.1 硬件事实

- 气阀接在 **MSR1616NT 的 DO 端子 15/16** 上（双线圈电磁阀：DOUT15/DOUT16 各控一个方向）；
- MSR1616NT DO 输出：**NPN、0.6A/路**，24V 电磁阀线圈（<0.2A）无需继电器：
  `+24V → 阀线圈 → DO15/16 端子`（线圈并联续流二极管，见手册接线注意事项）；
- 气泵：独立 24V 供电即常转（与控制 IO 无关），阀切换决定夹爪动作。

### 4.2 实测映射（控制器回读验证）

| 状态 | DOUT15 | DOUT16 | 命令序列 |
|---|---|---|---|
| 关闭 | 1 | 0 | `0x3601 {15,1}` {@ `0x3601 {16,0}` |
| 打开 | 0 | 1 | `0x3601 {15,0}` {@ `0x3601 {16,1}` |

实测往返：初始(1,0) → 写(0,1) 回读(0,1) → 写(1,0) 回读(1,0)，**双向翻转成功**。

## 6.2 手眼标定求解失败：根因与修复（2026-08-22 实测破案）

**现象**：UI 手眼页采了 8 帧棋盘格样本（每帧 RMS 0.46~0.84px，很干净），
点"求解并启用手眼矩阵"报 `OpenCV checkerboard hand-eye solver produced no valid candidate`。

**根因（两个叠加的 bug）**：

1. **姿态回读旋转约定与控制器相反（主因）**：代码用
   `Rz(yaw)·Ry(pitch)·Rx(roll)`（fixed XYZ），而控制器 A/B/C = **动系 X'Y'Z'
   （≡ 定系 ZYX），须用 `Rx(A)·Ry(B)·Rz(C)`**。→ 8 个位姿的旋转全部错掉。
   验证：修复后平移残差 190mm → 2.4mm，旋转 170° → 0.74°。
2. **对称棋盘 180° 角点歧义（次因）**：OpenCV 对对称棋盘无唯一"起始角点"，
   相机滚转跨过临界时角点对应翻转 180°（连同坐标系原点平移），单帧 PnP
   RMS 仍然 <1px 看不出问题。→ 样本分成两组内部完全一致（两两转动角差
   ≤1.5°）的簇 {0,5,7} 与 {1,2,3,4,6}，两簇之间差 ~140-178°——这就是
   "求解失败"的直接死因（残差检测把所有帧都当离群）。

**修复（已合入代码）**：

- `transforms.py` / `geometry.py`：新增 `transform_from_inexbot_abc` /
  `inexbot_abc_from_transform`（控制器约定，含正逆变换）；
  `nexbot_tcp.py read_state` 与 `tcp_pose.py` 全部改用它（UI 显示值将与
  示教器工具坐标 A/B/C 一致）；
- `hand_eye.py`：`_resolve_checkerboard_ambiguity()` 在求解前归一化 180° 分支
  （≤10 帧穷举 2^n，更多帧贪心），用 `T @ inv(M)` 生成第二候选
  （M = [diag(-1,-1,1), (cols·s, rows·s, 0); 0 1]，**注意原点偏移也变**）。

**验证结果**（对已存档的 8 帧重解）：5/8 帧 ≤2.4mm/≤0.74°，0/5/7 三帧
≈30mm（翻转帧残存误差，可能是采集时相机/板轻微挪动）→ 需要 **修复代码后
重新采集至少 8 帧**（推荐 10 帧），求解即会自动通过（歧义归一化在求解器内）。

**现场样本已存档**：`docs/手眼标定现场样本-20260822/`（8 张 PNG + 位姿 yaml，
供复现分析；本次破案的全部脚本思路也在此文档中可追溯）。

**后续（同日晚，第二批 16 帧）**：用户重拍 16 帧（11:53-11:56，含之前的 8+1 帧共 24 帧）。
诊断：**新 16 帧两两转动角差中位 0.6°/最大 2.6%（100%<5°），无 180° 歧义簇** ——
唯一障碍仍是姿态约定（这批仍是旧代码写入的 legacy 约定矩阵）。
用控制器约定重建后：**trans_rms=3.02mm / rot_rms=0.715° / max 6.02mm，15/16 帧达标**
（仅 s23 略超），完整解出：
`T_tcp_camera` 平移 ≈ (-102.6, 4.4, -161.1)mm —— 相机挂装在工具手 1 下方，符合物理。

**已落地**（commit 027d41c 之后追加）：
- `competition.yaml` `hand_eye.tcp_from_color_camera.valid=true` + 矩阵（附标定指标注释）；
- 工作样本文件 `output/hand_eye_samples_oak.yaml` 中 s9..s23 的 `base_from_tcp` 已修正为
  控制器约定（原值保留在 `base_from_tcp_raw_legacy` 字段）；
- 结论：**无需 AprilTag 辅助**；重启修复后的 pipeline UI → 手眼页直接【求解】即可通过
  （样本文件已修正）；后续新采样本用新代码自动正确。
- A4 AprilTag(25h9) 留作后备方案：若未来更换/重装相机，可切 pipeline 的 AprilTag
  靶标手眼模式，或贴在棋盘非对称角点做锚点（需把 tag_map dictionary 改为
  DICT_APRILTAG_25H9 并登记 tag id/位置）。
