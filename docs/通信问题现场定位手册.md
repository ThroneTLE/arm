# 通信问题现场定位手册

> 用途：现场出现"指令发了但机械臂没反应"这类问题时，**5 分钟内定位到是哪一层的问题**。
>
> 本手册的每个数字都在 2026-08-23 用两条独立路径核对过：解析工具跑一遍，
> 再用 `zcat | grep` 手工跑一遍，对不上的以 grep 为准。
> 结论标注【实测】/【推断】—— 不要把【推断】当【实测】用。

## 0. 为什么不查手册、不搜网站

**公开文档在这台机器上被推翻过至少 7 次。** 具体的、已经付出过代价的例子：

| 手册怎么说 | 本机实际 | 代价 |
|---|---|---|
| `0x4501/0x4502` 参数表里**没有** `acc`/`dec` | 这两个字段**必填**，漏发就 `参数错误` | 归档里 54 条 `指令[0x4501]参数错误` + 14 条 `[0x4502]`，排查了大半天 |
| 某文档页写 `coord` 2=用户 / 3=工具 | `coord=3` 是**用户坐标系** | 差点把整套坐标标定推倒重做 |
| `0x2314` = 急停（受控减速停） | 走 `Deadan_End`，伺服带电时**直接 PowerOff** | 2026-08-22 摔了一次机械臂 |
| 固件"是 RTL-22.07 体系" | 出厂配置目录名写着 **21.05.23-4.1.1** | 按 22.07 推导出的一串结论全部作废 |

规律很清楚：**手册描述的是产品系列，不是你面前这台控制器的这版固件。**
"文档没写 = 不支持"这条推理在本机一律不成立，反过来"文档写了 = 一定这样"也不成立。

**手册可以用来佐证，不能用来推翻实测。** 顺序永远是：先看地面实况，
有了实测结论之后，再去手册里找一句话把它解释通（解释不通就以实测为准）。

## 1. 三条地面实况渠道

三条渠道**看到的东西不一样**，不是三份同一信息的副本。选错渠道会得到"什么都没看到"，
而"什么都没看到"很容易被误读成"什么都没发生"。

```
            我们的 PC                          控制器 (192.168.1.200)
        ┌───────────────┐                  ┌────────────────────────┐
        │  oak_vision   │   TCP 6001/7000  │  teachBox 收发层        │
        │  ucs_grasp    │ ───────────────▶ │    ↓                   │
        │  nexbot_tcp   │                  │  ioControl 安全闸门 ★  │
        └───────────────┘                  │    ↓                   │
              ①帧日志                      │  robotJob 运动执行      │
         (我们发/收的字节)                 └────────────────────────┘
                                              ②控制器日志(全都看得见)
                                              ③0x2B03 报警推送(只有一部分)
```

★ **关键**：安全闸门的拒绝**不走 0x2B03**。归档里 `机器人1不在安全位置附近` 出现 20 次，
其中作为 0x2B03 报警推给我们的 **0 次**【实测】。也就是说——
**光看报警文本，永远看不到最常见的那种拒绝。**

### ① 控制器日志 —— 唯一能看见"控制器内部怎么想"的渠道

- **看得到**：安全闸门判决、伺服上下电链、作业启停、操作模式切换、每条收到的指令字。
- **看不到**：字节层面的东西（CRC、粘包、半截帧）——控制器已经解析完了才记录。
- **代价**：要从示教器导出（见第 4 节），拿不到实时数据。
- **什么时候用**：**默认先用这条。** 机械臂不动、报错看不懂、指令像是被吞了，都先查它。

### ② 我们这端的帧日志 —— 唯一能看见"线上真实字节"的渠道

- **看得到**：我们**实际发出去**的每一个字节、CRC 对不对、收到的帧是不是完整。
- **看不到**：控制器内部为什么拒绝（那在渠道①里）。
- **代价**：默认**关闭**，要设环境变量重启程序才有；只记录我们这个进程的收发。
- **什么时候用**：怀疑**"我们发的东西本身就是坏的"**时。
  典型：控制器**完全没有任何反应**（连报警都没有）、换了台机器就好了、偶发性失败。

> **它回答的问题只有一个**：坏的是我们发的字节，还是控制器不认这条指令？
> CRC 全通过 = 字节是好的，别去改控制器配置，去看渠道①。
> CRC 有失败 = 问题在我们这端 / 链路，别去猜控制器。

### ③ 控制器的 0x2B03 报警文本 —— 最快，但覆盖不全

- **看得到**：参数错误、伺服故障、限位、作业冲突 —— 都带控制器自己的原文。
- **看不到**：安全闸门拒绝（0 条，见上）、以及任何"控制器认为这是正常流程"的拒绝。
- **代价**：几乎没有，界面上/帧日志里当场就有。
- **什么时候用**：**有报警文本时先读它**，它通常直接就是答案。
  但**没有报警 ≠ 没有问题**，这是本手册最重要的一句话。

> `0x2B03` 的真实文本在 JSON 的 **`data` 键**里，不是 `code`。
> `code` 是数字（如 25530 = 参数错误），同一个 code 覆盖多种指令，**别按 code 反查含义**。

## 2. 每条渠道的具体命令

### 2.1 控制器日志 —— `read_controller_logs.py`

**只读**：不 import 任何运行时模块、不写文件、不连网络。可以随便跑。

```bash
# 现有归档（2026-08-22 现场，30 个文件 / 80 万条记录，约 4 秒跑完）
ARCHIVE=docs/现场备份-20260822/controlLogs08-22-22-16

# ★ 第一条永远先跑这个：一页纸看完全局
$ARMPY competition_pipeline/scripts/read_controller_logs.py $ARCHIVE --summary
```

`--summary` 会打印：数据源与时间覆盖 / 级别分布 / **运动指令结局 × 操作模式**（最有用的一张表）/
指令字 Top25 / 操作模式停留时长 / 事故链 / **安全位置偏差** / 报警 Top15。

```bash
# 只看某几条指令字（十六进制，可逗号分隔）
$ARMPY competition_pipeline/scripts/read_controller_logs.py $ARCHIVE --cmd 0x3007,0x4502

# 掐时间窗（几种写法都行：13:30 / 08-22 13:30 / 2026-08-22 13:30:05）
$ARMPY competition_pipeline/scripts/read_controller_logs.py $ARCHIVE \
    --cmd 0x3007 --since '08-22 13:30' --until '08-22 13:40'

# 只看报警与被拒的指令
$ARMPY competition_pipeline/scripts/read_controller_logs.py $ARCHIVE --errors-only --tail 40

# ★ 看"一次拒绝之后控制器都干了什么"——摔臂/掉伺服就查这个
$ARMPY competition_pipeline/scripts/read_controller_logs.py $ARCHIVE \
    --chain --since '08-22 13:34' --until '08-22 13:35'

# 按正文搜（正则），--context 打印命中行前后各 N 行原始日志
$ARMPY competition_pipeline/scripts/read_controller_logs.py $ARCHIVE \
    --grep 不在安全位置 --context 12
```

> ⚠️ **`--grep` 收的是正则不是字面量。** 日志正文满屏 `[0x3007]`，直接粘进去
> 会被当成**字符集**（匹配"含 0/x/3/7 任一字符的行"），静默返回几十倍的错结果。
> 写 `--grep 0x3007`，不要写 `--grep '[0x3007]'`。工具现在会报错拦住你，但记住这条更省事。

其它开关：`--raw`（打原始记录而非事件表）、`--with-heartbeat`（默认隐藏 0x7266/0x7267，
它们占了 2/3 的事件）、`--window SEC`（判定运动结局往后看多久，默认 2 秒）。

**实跑样例**（示教 vs 远程的差别一眼可见）：

```
时间戳                   端口  向    指令字  含义                        模式  结果
2026-08-22 13:31:09.616  6001  收到  0x3007  回复位点 GO_RESET_POSITION  示教  已启动
2026-08-22 13:34:18.604  6001  收到  0x3007  回复位点 GO_RESET_POSITION  远程  被拒:安全闸门
```

### 2.2 我们这端的帧日志 —— `NEXBOT_FRAME_LOG` + `decode_frames.py`

**默认关闭，零开销。** 不设环境变量时收发路径一个字节都不改
（`send_frame` 完全不动；`read_frame` 开头多 4 条字节码，实测差值淹没在噪声里）。

```bash
# 开日志跑 UI（任何入口都一样，加个环境变量即可）
NEXBOT_FRAME_LOG=/tmp/frames.log ./tool/visual_grasp_pipeline/run_oak_vision_node.sh

# 解码 + 独立复算 CRC
$ARMPY competition_pipeline/scripts/decode_frames.py /tmp/frames.log

# 只看坏帧（脚本有坏帧时 exit=1，可以直接写进判断）
$ARMPY competition_pipeline/scripts/decode_frames.py /tmp/frames.log --bad-only

# 只看某几条指令字 / 连原始字节一起打
$ARMPY competition_pipeline/scripts/decode_frames.py /tmp/frames.log --only 0x4502,0x2B03 --show-hex

# 手上只有一段 hex（比如从别人截图里抄来的），直接解
$ARMPY competition_pipeline/scripts/decode_frames.py --hex '4e66 0010 2311 7b22...'
```

输出长这样，**两个 CRC 是独立算出来的**，不是复读帧里那个：

```
2026-08-23 01:12:12.360 --> 36699 0x2311 上位机使能(伺服上电)
    CRC 通过 0x62204A30
    {"robot": 1}

== 汇总 ==
帧数 119  |  CRC 通过 118  |  CRC 失败 1  |  CRC 无法判定 0  |  不成帧的碎片 0
结论: 有 1 帧 CRC 对不上 —— 问题在字节层, 先查我们这一端, 别去改控制器配置。
```

**怎么读这个结论**：

| 汇总说 | 意思 | 下一步 |
|---|---|---|
| 全部 CRC 通过 | 我们发的字节是好的 | 控制器**不认**这条指令 → 转渠道① |
| 有 CRC 失败 | 字节在我们这端或链路上就坏了 | 查我们这端，**别动控制器配置** |
| 有"不成帧的碎片" | 进程被杀 / 半截帧 | 通常是上游崩了，看进程日志 |

**抓包路线**（只有在怀疑"程序以为发了但网卡上没有"时才需要）：

```bash
sudo tcpdump -i eth0 -s 0 -w /tmp/c.pcap 'tcp port 6001 or tcp port 7000'
$ARMPY competition_pipeline/scripts/decode_frames.py /tmp/c.pcap
```

- **`-s 0` 千万别漏**。默认 snaplen 会把大帧截断，截断的帧必然误报 CRC 失败，
  你会花一小时排查一个不存在的问题。（脚本检测到疑似截断会提示。）
- **只支持经典 pcap，不支持 pcapng**。`tcpdump -w` 默认就写经典 pcap，正常流程不受影响；
  喂 pcapng 会明确报错让你重抓，不会瞎猜。
- 分段的帧会按 TCP 序号重组，重传会去重。

> ⚠️ **帧日志无上限、无轮转**。典型帧行 455 字节，20 Hz 状态轮询连跑 8 小时 ≈ **250 MB**。
> **用完就把环境变量去掉**，别让它整个上午开着。

### 2.3 0x2B03 报警文本

不需要单独的工具，两条渠道都能看：

```bash
# 从控制器日志里看（含 code 与出现次数）
$ARMPY competition_pipeline/scripts/read_controller_logs.py $ARCHIVE --errors-only --tail 40

# 从帧日志里看（实时，控制器主动推的原文）
$ARMPY competition_pipeline/scripts/decode_frames.py /tmp/frames.log --only 0x2B03
```

帧日志里会把原文单独拎出来一行：

```
<-- 37617 0x2B03 报警推送(真实文本在 JSON 的 data 键)
    {"code": 25530, "data": "指令[0x4502]参数错误", "kind": 2, "param": [...], "robot": 0}
    !! 控制器报警原文: 指令[0x4502]参数错误
```

## 3. 症状 → 先查哪条渠道 → 大概会看到什么

> 用法：**从上往下找第一条对得上的**，按"先查"那列走一步就够，别一上来三条渠道全开。

| 症状 | 先查 | 命令 | 大概会看到什么 | 多半是什么 |
|---|---|---|---|---|
| **机械臂完全不动，但夹爪照常开合** | ① 控制器日志 | `--summary` 看"运动指令结局 × 操作模式" | `mode=1 远程 → 被拒 34 / 已启动 0`；正文 `机器人1不在安全位置附近，不予与执行。(pos[1])` | **在远程模式**。夹爪走 `0x3601` DOUT 是另一条码路，所以照常。→ **切回示教模式** |
| 同上，但**已经在示教模式** | ① 控制器日志 | `--errors-only --tail 40` | `指令[0x4501]参数错误(25530)` | 漏发 `acc`/`dec`（手册没印）。归档里 `0x4501` 示教下 14 次栽在这 |
| **指令像是没收到**（控制器毫无反应，连报警都没有） | ② 帧日志 | `--bad-only` | CRC 失败 / 半截帧 / 不成帧的碎片 | 字节层。CRC 全通过就说明发出去了，转渠道① |
| 同上，且**帧日志里那条指令根本没出现** | ② 帧日志 | `--only 0x4502` | 空 | 我们的代码压根没发（闸门拦下了 / 分支没走到），**不是通信问题** |
| **报错文本看不懂** | ③ 0x2B03 | `--errors-only` 或 `--only 0x2B03` | 见 3.1 的对照表 | 直接查表 |
| **有拒绝但没有任何报警文本** | ① 控制器日志 | `--chain --since ... --until ...` | `不在安全位置` → `触发stop` → `JobClear` → `脉冲使能=0` → `Deadan_End` | 安全闸门。**它不发 0x2B03**，只在日志里 |
| **位姿读数明显不对**（差 ~57 倍，或姿态转了上百度） | ③ 帧日志里的 0x2A03 | `--only 0x2A03 --show-hex` | 同一帧里既有 `pos` 又有 `posDeg`，且 `deg:1` | **读错字段了**，见 3.2 |
| 位姿读数**数值合理但位置不对** | ① 控制器日志 | `--cmd 0x2201` | `{"coord":3,...}` | `coord` 选错坐标系。`3`=用户坐标系 |
| **连接被拒 / 频繁掉线** | ① 控制器日志 | `--grep socket --context 4` | `socket6001网络已连接。` → `"net6001"网络接收:接收错误` → `socket6001网络已断开。` | 见 3.3 |
| **伺服莫名其妙掉电 / 手臂坠落** | ① 控制器日志 | `--chain` | `Deadan_End(Robot_Group_State=1)` → `PowerOff` | 见 3.4 |

### 3.1 报警文本速查（全部来自本机归档，括号内是归档里的出现次数）【实测】

| 报警原文 | 次数 | 真正的意思 |
|---|---|---|
| `指令[0x4501]参数错误` | 54 | **漏发 `acc`/`dec`**（正确顺序 `robot→vel→acc→dec→coord→pos[7]`）。不是坐标越界 |
| `指令[0x4502]参数错误` | 14 | 同上 |
| `机器人1伺服映射错误` | 99 | 伺服没连上/没配好，跟你发的指令无关 |
| `与从站通信失败` | 46 | EtherCAT 从站掉了。先看物理连接与上电顺序 |
| `机器人1映射的伺服N不存在` | 23×6 | 同上，控制器还没枚举到伺服 |
| `伺服未连接` | 23 | 同上 |
| `第1个伺服不在OP状态，请等待` | 5 | **等一下再发**，不是错误 |
| `伺服当前实际连接数目与配置数目不符，请等待` | 4 | 同上，开机过程中的正常态 |
| `机器人1作业文件正在运行中` | 18 | 上一条运动还没走完。**不是拒绝，是排队冲突** —— 等它结束或先 `0x2401` 停止 |
| `机器人1的N轴点动位置达到极限` | 5+ | 真的到限位了，换个方向点动 |
| `机器人1伺服错误(0F15 ×6)` | 3 | **六轴同时报 0F15** = 跟随误差过大。**这是摔臂那次的起因**，通常因为一条指令要求的运动量太大（例如把度当弧度发） |
| `指令[0xNNNN]不存在` | 2×3 | 本机固件不支持这条指令字。别再试了 |

> ⚠️ **`参数错误` 不代表"你的坐标不对"。** 归档里 68 次参数错误，全部是字段少发，
> 一个都不是坐标越界。看到它先数字段，别去改坐标。

### 3.2 位姿读数：度 / 弧度的边界【实测】

这是 2026-08-22 摔臂的直接原因，值得单独看一眼真实帧：

```
0x2A03 应答: {"coord":3, "deg":1,
              "pos":    [-268.262, 56.209, 290.243,  3.101525,  0.387617, -3.123660, 0.0],
              "posDeg": [-268.262, 56.209, 290.243, 177.704...,      ...,       ...]}
```

- 同一帧里 **`pos` 的 A/B/C 是弧度，`posDeg` 的 A/B/C 是度**（3.101525 rad × 57.29578 = 177.70°，逐位对得上）。
- **`deg:1` 不表示 `pos` 是度**。这个字段极具误导性，别拿它做判断。
- 7000 端口：**只有 `realPosACS` 是度**；`realPosUCS` / `realPosPCS` 的 A/B/C 是**弧度**。
- 我们这端的约定：`current_pose()` 返回**度**，`current_pose_rad()` 返回**弧度**，
  `move_to_ucs()` 收**弧度**，`check_abc_is_radians()` 会拦住度数值。

**症状识别**：读数差 57.3 倍 → 度/弧度弄反了。姿态要转上百度而 XYZ 只走几十毫米
→ **立刻停手**，这正是摔臂那次的形状（六轴同时 0F15 → 下电 → 坠落）。

### 3.3 连接被拒 / 掉线【实测】

归档里的真实序列长这样：

```
socket6001网络已连接。
-->>6001收到指令[0x2314],${"robot":1}$
"net6001"网络接收:接收错误
socket6001网络已断开。
```

排查顺序：

1. **端口对不对**：`6001` 是实时指令通道，`7000` 是状态查询。**`6000` 是关闭的**，
   连它永远超时【实测】。
2. **是不是被别的程序占住了**：控制器同一端口的并发连接数有限，
   示教器自己也在连。先把其它进程关掉再试。
3. **是不是我们自己发了 `0x2314` 之后被断开的**（上面这段就是）。
4. 网络层：`ping 192.168.1.200`。控制器 `.200`，示教器 `.245`。

### 3.4 伺服掉电 / 手臂坠落【实测】

`--chain` 打出来的完整链：

```
机器人1不在安全位置附近，不予与执行。(pos[1])     ← 起因
远程IO控制：机器人1触发stop。
机器人1执行JobClear命令
设置脉冲使能为 0
机器人1开始执行Deadan_End命令(Robot_Group_State=1)  ← ★ 看这个数字
1111机器人1执行PowerOff命令=0                       ← 真的下电了
222机器人1执行PowerOff命令=0
```

**`Robot_Group_State` 决定会不会真的坠臂**【实测，20/20 核对】：

| 值 | 含义 | 后果 |
|---|---|---|
| `0` | 伺服本来就没上电 | 走完停止链就结束，**不会下电**（本来就没电） |
| `1` | 伺服带电 | **→ PowerOff，伺服失力，伸展着的手臂靠自重坠落** |
| `2→3` | 运行中 | 观察到一次走的是受控停，未 PowerOff |

所以"拒绝即下电"这个说法要精确成：**拒绝一定走停止链；当时带电才真下电。**
归档 20 次闸门拒绝里，18 次走了停止链，只有 **2 次**（13:34:18、13:36:15）真的 PowerOff
——那两次正是伺服带着电的时候，也正是最危险的时候。

> **`PowerOff` 的计数会骗人**：同一次下电打两条日志（`1111...` 和 `222...`），
> 而且 `333333333机器人1执行PowerOff命令=1` 是**一段运动正常走完**的回调，
> 不是下电。归档里 516 条 PowerOff 实际只对应 **258 次真下电**。
> `--summary` 已经替你除过了，直接读它给的数。

### 已经确定的部分【实测，来自 2026-08-22 那次导出的产物】

导出物会落到**插在示教器上的 U 盘**，然后在 Linux 上挂载到
`/media/<用户名>/<U盘卷标>/`（上次是 `/media/throne/UBUNTU 20_0/`）。

导出会产生**两种目录，命名都带时间戳 `MM-DD-HH-MM`**：

| 目录 | 内容 | 什么时候需要 |
|---|---|---|
| `controlLogs<MM-DD-HH-MM>/` | `logInfo.0` … `logInfo.29`，**gzip 压缩**，30 个文件滚动覆盖 | **通信问题查这个** |
| `SystemBackup<MM-DD-HH-MM>/` | `config.db`、`configFile-<固件版本>-<时间戳>/`（含 `global.json`）、`nrc.out`、`robotJob<...>/`（作业文件） | 查配置（安全闸门、限位、坐标系标定） |

已知的行为特征：

- `logInfo.N` 是**滚动覆盖**的，30 个文件循环用。上次那份 30 个文件覆盖了
  2026-04-09 到 2026-08-22，**80 万条记录**，说明容量不小，但**别指望它保留很久**
  —— 出问题后**尽早导**，一次密集调试就可能把早期记录冲掉。
- 文件是 gzip 压缩的，但**不带 `.gz` 后缀**。`read_controller_logs.py`
  两种都吃（压缩/未压缩自动判断），不用先解压。
- `configFile-` 后面跟的就是**固件版本号** —— 这是确认固件版本最可靠的来源，
  比任何文档都可信（本机 `21.05.23-4.1.1`）。

拷回仓库后直接跑：

```bash
cp -r '/media/throne/<U盘卷标>/controlLogs08-23-XX-XX' /tmp/
$ARMPY competition_pipeline/scripts/read_controller_logs.py /tmp/controlLogs08-23-XX-XX --summary
```

> 工具接受**目录**，也接受**单个 `logInfo.N` 文件**。

## 5. 已知指令字含义表

**证据等级的判定方法**：在本机归档（`controlLogs08-22-22-16`，80 万条记录）里
grep 该指令字的出现次数与上下文。出现过且行为可观察 = 【实测】；
没出现过、只来自手册或我们自己的代码 = 【推断】。括号内是归档出现次数。

### 5.1 端口 6001（实时指令通道）

| `0x7266` / `0x7267` | 心跳（示教器→控制器）/ 回复 | 【实测】(111525 / 111521) |

★ **`0x2101` 是判断操作模式的唯一可靠来源。**
曾经以为 `startRobotJobTask(... mode=N ...)` 里的 `mode` 是操作模式 —— **错的**，
全量 99 条里 **99 条都是 0**，包括那些在远程模式下被拒的指令。
真正的模式源是 `-->>收到指令[0x2101],${"mode":N}`（控制器同一毫秒回 `设置操作模式为N%`）。
按 `0x2101` 判定后与现象**零例外自洽**：18 次拒绝全在 `mode=1`，
13:31:09 那条 `mode=0` 的 `0x3007` 顺利执行。

★★ **`0x2314` 的精确行为**（归档 6 次，逐条核对）：
`Deadan_End` **6/6** 触发；`PowerOff` **2/6** —— 且那 2 次正是
`Robot_Group_State=1`（伺服带电）的时候。另有 1 次 `state=2→3`（运行中）走的是受控停。
**安全结论不变**：手臂伸展且带电时发它 = 直接坠落。真正的急停只能是**示教器上的物理按钮**。

★★★ **`0x2F16` 是安全闸门拒绝在线上的唯一签名。**
归档里 `不在安全位置` 20 条、`0x2F16` 推送 20 条，**严格 1:1，且每条 `0x2F16`
的前一行都是那句拒绝**【实测，20/20】。因为拒绝**不发 `0x2B03`**，所以——
**在帧日志里看到一条没请求过的 `0x2F16`，就等于收到了"安全闸门拒了你"。**
它的载荷里 `currentPos` 有 12 位小数而 `safePos` 只有 5 位，肉眼看满屏都是"不一样的数",
别被骗——用 `--summary` 的"安全位置偏差"段落看**逐轴差值**。

### 5.2 端口 7000（状态查询通道）

| 指令字 | 含义 | 等级 |
|---|---|---|
| `0x9512` | 状态批量查询（`queryType: realPosUCS / realPosMCS / realPosACS`） | 【实测】(52031) |
| `0x9513` | `0x9512` 的应答 | 【实测】我方收发正常；控制器日志不记录出向应答，故归档计数为 0 |
| `0x1E00` | 24.03 体系的状态查询 —— **本机不支持** | 【实测】(3) 3/3 回 `上位机服务:命令字0x1e00不存在`，别用 |

**本机已确认不支持的指令字**【实测】：`0x1E00`（回 `E/HostServ 命令字不存在`）、
以及 `0x5716` / `0x9010` / `0x9025` / `0x9040`（各 2 次，回 `0x2B03: 指令[0xNNNN]不存在`）。
注意这两类的报错渠道不同：`0x1E00` **只写日志，不推 0x2B03** —— 又一个
"渠道③看不到、渠道①看得到"的例子。

### 5.3 帧格式【实测】

```
0x4E66 | Length u16 BE | Command u16 BE | JSON data | CRC32 u32 BE
        └──────────── CRC 覆盖范围 ────────────┘
```

- 同步字 `0x4E66`；CRC32 是标准 `zlib.crc32`，**覆盖 length + command + data**，
  不含同步字本身。
- 官方示例帧复算结果 `0x9090FA38`，对得上 —— 这是 CRC 算法正确的交叉验证。

### 5.4 归档里出现过但**含义未知**的指令字

这些在本机跑得很频繁，但我们**没有确认过它们是干什么的**，
`read_controller_logs.py` 会标 `(未定名, 见示教器手册)`。**别去猜**：

```

0x2E02 (272)    0x380B (244)    0x3118 (243)  0x3305 (214)  0x7602 (182)
0x5722 (182)    0x5725 (182)    0x3114 (132)
```

它们全部是**示教器本机**发的（端口列是空的，不是 6001），
所以跟我们的通信问题基本无关。看到它们刷屏是正常的。

## 附 A. 本手册数字的复核方法

不要相信工具的自证。每个数字都能用一行 `grep` 独立核对：

```bash
cd docs/现场备份-20260822/controlLogs08-22-22-16
zcat -f logInfo.* > /tmp/all_logs.txt          # 30 个文件摊平成 112 万行

grep -c "不在安全位置" /tmp/all_logs.txt                    # 20（含 2 条 08-19 旧会话）
grep -cP '发送指令-->>\[0x2f16\]' /tmp/all_logs.txt          # 20  ← 与上面 1:1
grep -A3 -P "\[0x2314\]" /tmp/all_logs.txt | grep -c PowerOff   # 2（不是 6）
grep -oP '收到指令\[0x[0-9A-Fa-f]{4}\]' /tmp/all_logs.txt | sort | uniq -c | sort -rn | head -30
grep -P '0x2b03' /tmp/all_logs.txt | grep -oP '"data":"[^"]*"' | sort | uniq -c | sort -rn
```

> 注意 `zcat -f`：归档文件是 gzip 但**不带 `.gz` 后缀**，`-f` 让它对未压缩文件也不报错。
